# 预聚合评估 — 历史数据增长后是否需要物化聚合

> 结论先行：**当前不需要预聚合。** 实测聚合成本远低于感知阈值，瓶颈一直在「读事件日志」而不在「算聚合」。
> 若未来会话量增长到万级，优先做的是**分段物化**（按周），而不是全量预聚合表。
> 评估日期：2026-10-23 · 数据：作者本机 483 个会话 / 索引 0.51 MB

## 一、为什么要评估

用户提问：随着历史数据增加，是否可以把历史数据预先聚合？

直觉上「数据越多越慢，所以预聚合」是合理的。但要看**慢在哪一层**。本插件有三级成本：

| 层级 | 成本 | 触发频率 | 能否预聚合省掉 |
| --- | --- | --- | --- |
| 1. 读事件日志（`readSession`） | **数百毫秒～数秒/会话** | 冷读 / 重校验 | ✅ 能（但已由 v1.0.4 的节流解决） |
| 2. 聚合（`aggregate`） | **7–9 ms / 483 会话** | 每次缓存 miss | ⚠️ 可省，但收益小 |
| 3. 序列化 + 传输（`present` → JSON） | ~7 ms / 155 KB | 每次请求 | ❌ 预聚合省不掉 |

**关键事实：第 1 层才是 4 分钟级成本，第 2 层是毫秒级。** 预聚合只能优化第 2 层。

## 二、实测数据

### 2.1 聚合成本 vs 会话数

用真实索引行复制放大模拟（同一台机器，Node 22）：

| 会话数 | `aggregate` 耗时 |
| --- | --- |
| 483 | **9.3 ms**（5 次均值） |
| 966 | ~26 ms |
| 2,415 | ~47 ms |
| 4,830 | ~99 ms |
| 9,660 | ~148 ms |

近似线性，斜率约 **0.015 ms/会话**。即使 1 万个会话，聚合也只有 **~150 ms**。

### 2.2 不同区间的成本几乎相同

| 区间 | 耗时 |
| --- | --- |
| 近 7 天 | 53 ms（含 JIT 预热） |
| 近 30 天 | 18 ms |
| 近 90 天 | 26 ms |
| 全部 | 19 ms |

说明聚合是**全量扫一遍再按区间过滤**，不是按天累加。这反过来说明：
**按区间预聚合的收益有限**（本来就只扫一遍），而按天预聚合反而要额外维护时序表。

### 2.3 索引文件构成（预聚合能省的空间）

| 项 | 大小 / 占比 |
| --- | --- |
| 索引文件 | 0.51 MB |
| `JSON.parse` | 5.2 ms |
| 单行中位 | 1.0 KB（最大 2.3 KB） |
| `models` 字段占全文 | **22.2%** |
| `hourTokens` 字段占全文 | 5.4% |

索引本身很小。**预聚合表如果和索引分开存，反而增加一次 I/O + 一份需要保持一致的数据。**

### 2.4 当前真实响应耗时（3080 实例，483 会话）

| 请求 | 耗时 |
| --- | --- |
| `snapshot?days=7` | 4–37 ms |
| `snapshot?days=30` | 31 ms |
| `snapshot?days=90` | 36 ms |
| `report.html` | 30 ms |

**全部远低于 100 ms 的感知阈值。** 用户不可能察觉「预聚合能省下的那 10 ms」。

## 三、如果做预聚合，代价是什么

| 代价 | 说明 |
| --- | --- |
| **一致性** | 活会话每来一个事件都要更新预聚合表；否则数字会和明细表对不上（本插件最忌讳「编数字」） |
| **维度爆炸** | 预聚合要覆盖 `days / from-to / tz / scope(all·main·subagent) / workspaceAliases / modelAliases / pricing / activeModelMetric` 的组合，缓存 key 空间很大 |
| **时区** | 同一份数据在不同 `tz` 下归属日期不同，「按天预聚合」在非 UTC 时区会错位 |
| **失效复杂度** | 模型回填、索引重建、别名修改、价格表变更都要级联失效 |
| **收益** | 最多省 10–150 ms（取决于会话量），而首次构建/冷读是秒级 |
| **违背原则** | README 承诺「不编数字」，预聚合最容易引入的就是「聚合表和明细不一致」 |

## 四、真正该做的（按优先级）

| 优先级 | 事项 | 状态 |
| --- | --- | --- |
| ✅ 已做 | **冷读节流**（v1.0.4）：TTL 12h → 7d + 只重校验近 30 天活跃会话。`buildMs` 49 s → 1.5 s | 已完成 |
| ✅ 已做 | **快照 SWR**（v1.0.5）：活会话事件后不再必然 miss | 已完成 |
| 建议（未做） | **增量聚合**：缓存「上次聚合的 rows 快照 + 结果」，只在有行变化时重算受影响的部分 | 等会话量到 2 千级再考虑 |
| 建议（未做） | **分段物化**：把「已封存的历史周」预聚合成不可变段，只对「最近 N 天」实时算 | 万级会话时再考虑 |
| 建议（未做） | **索引瘦身**：`models` 占 22%，可考虑编码为数组而非对象 | 低优先级 |

## 五、触发条件（什么时候该重新评估）

满足**任一**条件时再做预聚合：

1. `snapshot` 的 p95 稳定超过 **200 ms**；
2. 会话数超过 **5,000**（按 0.015 ms/会话推算，聚合约 75 ms + 序列化，接近可感知）；
3. `buildMs` 再次超过 **10 s**（说明第 1 层又退化了，但应先查冷读而不是加预聚合）。

当前三项均远未触发：483 会话 / `buildMs` 1.5 s / `snapshot` p95 < 40 ms。

## 六、如何复测

```bash
# 聚合成本（真实索引行）
node -e "
import('./src/aggregate.js').then(async (m) => {
  const fs = await import('node:fs');
  const idx = JSON.parse(fs.readFileSync(process.env.HOME + '/.dsh/workload-report/index-v7.json','utf8'));
  const rows = Object.values(idx.rows);
  const t = () => { const s = performance.now(); m.aggregate(rows,{days:30,timeZone:'Asia/Shanghai'}); return performance.now()-s; };
  t(); console.log('会话数', rows.length, '聚合', [1,2,3,4,5].map(t).reduce((a,b)=>a+b,0)/5, 'ms');
});
"

# 线上响应耗时
for d in 7 30 90; do curl -s -o /dev/null -w "days=$d %{time_total}s\n" "http://127.0.0.1:3080/workload-report/v1/snapshot?days=$d&tz=Asia%2FShanghai&scope=all"; done
```
